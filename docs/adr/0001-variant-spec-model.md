# 规格组合用 JSON 列承载维度元数据，不建维度表

## 背景与决定

商品的规格由两个维度（如颜色、尺码）组成，每个规格组合单独定价与库存。我们决定：

- **商品级**用 JSON 列存维度元数据（维度名与选项集合），不建立 `spec_dimensions` / `spec_options` 维度表。
- **组合级**用 `option1_value` / `option2_value` 两个普通列存选项值，按商品声明的维度顺序解释；不另存一份组合的 JSON 表示。

## 理由

- **查询需求**：本期筛选只涉及商品类型、价格区间、销量，没有任何按维度或选项的查询；维度表带来的多一层 join 没有消费方。
- **数据规模**：24 件商品、每件两维、每维两到四个选项，规范化后维度表的行数在百级，收益可以忽略。
- **维护成本**：新增商品时维度元数据随商品一起写入，不需要先维护全局字典；不同商品类型可以有不同维度名（鞋用颜色/尺码，数码用容量/颜色）。

## 考虑过的其他方案

- **维度表 + 选项表**：规范化最彻底，但多两张表、多一层 join，且本期无消费方。
- **固定 `option1_name` / `option1_value` 四列**：能表达不同维度名，但固定为两组字段，且没有商品级维度元数据（选项集合、顺序、展示名）。
- **组合级再存一份 `specs` JSON**：与两个选项列重复，两套表示需要同步，已放弃。

## 后果

- 唯一性由 `UNIQUE(product_id, option1_value, option2_value)` 保证，`sku` 另有独立唯一索引；不依赖 JSON 内容，也不需要分隔符或哈希。
- 两列使用 `utf8mb4_0900_bin`（按字符码值比较、尾随空格视为有效字符），应用层采用严格字符串比较；选项值以商品声明的为准，组合必须精确引用，校验时拒绝首尾空白、保留大小写与全半角。
- 已有商品调整维度顺序时，需要同步转换现有组合的选项值列。
- JSON 列只保证 JSON 语法合法（MySQL 会校验），维度归属、选项合法性等业务规则必须由应用层校验。
- 若后续出现按规格维度筛选的需求，需要重新评估查询、索引与数据模型；JSON 数据本身可查询，不必然要拆表。
