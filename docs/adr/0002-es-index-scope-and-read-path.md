# ES 只存检索与排序字段，展示字段回 MySQL 补齐

## 背景与决定

C37 已定「价格、库存一律走 MySQL」。Phase 4 的关键词搜索改走 Elasticsearch，但列表展示字段（展示价、展示原价、售罄、评分、销量、封面图）仍以 MySQL 为权威。

决定：ES 文档只存检索文本（`name` / `brand` / `model` / `categoryName`）、`slug`、`productId`，以及筛选排序所需的 `categorySlug`、`sales`、`displayPriceCents`。命中、筛选、排序、分页由 ES 完成；展示字段由 MySQL 按 ES 命中顺序批量补齐。

ES 中的 `displayPriceCents` 与 `sales` 是重建时的快照，不做增量同步（C40）；数据变更后必须重建索引。

例外：商品联想（#22）的 `name` / `brand` 直接取自索引，用于检索结果展示。这是本 ADR「展示字段回 MySQL」的既定例外，不改变价格、库存等仍以 MySQL 为权威的规则。

## 理由

- 与 C37 一致，价格与库存只有一个权威来源，避免两套价格规则长期漂移。
- 展示价是派生值（有库存优先 → 价升 → id 升），MySQL 侧已有唯一实现（`src/db/product-summary.ts`）；回 MySQL 补齐可直接复用，不必在重建脚本里复刻一份。
- 筛选排序字段仍进 ES，因此筛选边界与排序规则在 ES 侧完成，不需要把全量商品拉回应用层排序。

## 考虑过的其他方案

- **ES 存全量展示字段**：一次查询即可返回完整列表项，派生查询同样可以复用 MySQL 现有实现；额外成本是要维护一份展示快照的一致性（每次数据变更都要跟进重建），且与 C37「价格一律走 MySQL」的表述冲突。
- **ES 只存检索字段、排序回 MySQL**：需要把命中集合全部取回再排序分页，16 件虽可行，但违背「分页由 ES 完成」的意图，规模一涨就失效。

## 后果

- 每次关键词搜索多一次 MySQL 批量查询（按命中 `slug` 集合做一次 IN 查询）。
- 一致性由两侧共同保证：ES 侧的筛选排序字段在重建时写入，展示字段由 MySQL 补齐；验收按固定查询矩阵双路径比对。
- 若将来出现必须由 ES 独占返回的字段，需先改本 ADR。
